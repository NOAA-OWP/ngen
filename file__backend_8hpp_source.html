17File-based `RecordBackend` implementation.
18
19Persists records using the v0.2 wire format defined in
20`src/utilities/bmi/wire_format.hpp`: each record is a fixed-size
21prefix + id bytes + payload bytes, written sequentially to a
22single append-mode file. A FileBackend maintains an in-memory
23index keyed by `Record::id`, built on the first `reader()` call
24by walking the file once, and services `find_*` queries via
25index lookup + per-record seek.
26
27Per-path sharing
28----------------
29`FileBackend` is **shared per path** via a process-static
30registry. `FileBackend::create(path, scope)` is a `get_or_create`
31factory: the first caller for a given path allocates the backend
32and registers the resulting `shared_ptr` under a `weak_ptr` slot;
33subsequent callers for the same path receive the same
34`shared_ptr`. The backend (and its index, and its write fd) die
35when the last caller drops their handle; the `weak_ptr` slot
36becomes recoverable and is opportunistically pruned on the next
37lookup.
38
39This pattern is what makes N independent clients on the same
40checkpoint file viable at scale: N callers that each ask the
41registry for a backend at the same path share **one** index,
42**one** write fd, and **one** mutex-serialized write critical
43section, instead of paying N times.
44
45Two-layer scope filtering
46-------------------------
47`IdPredicate` filtering happens at two distinct layers:
48
49 - **Index scope** — passed to `create(path, scope)`. Records
50 whose id does not satisfy the predicate are never added to
51 the in-memory index.
52
53 Each `create()` call registers its scope. The index is built
54 on the first `reader()` call from the union of every non-empty
55 registered scope; empty scopes drop out of the union so a
56 save-only caller can pass `{}` to mean "no opinion." With no
57 non-empty scope registered, the fallback is "index everything."
58 `create()` calls arriving after the first `reader()` still
59 record but do not retroactively broaden the built index.
60
61 - **Read scope** — passed to `reader(scope)`. Per-Reader
62 predicate applied at `find_*` time. A record is returned iff
63 *both* the index-scope predicate (already enforced by not
64 being in the index) AND the read-scope predicate accept its
65 id. Lets a single Reader narrow further within a backend
66 whose index scope was deliberately broadened.
67
68Durability semantics
69--------------------
70`RecordBackend`'s abstract contract distinguishes `Durability::strict`
71(synchronous + durable) from `Durability::relaxed` (best-effort
72durability, errors *may* be deferred to `finalize()`). FileBackend
73fills in those two parameters as follows:
74
75 - **`strict`**: `commit()` calls `::fsync()` on the owned fd
76 before returning, ensuring kernel page-cache pages reach the
77 storage device. All write- and commit-side I/O failures
78 surface synchronously through the call's `expected<>` return
79 arm. Matches the abstract contract exactly.
80
81 - **`relaxed`**: `commit()` skips `::fsync()` — bytes are
82 handed to the kernel and may sit in the page cache when
83 `commit()` returns. The OS will eventually flush, but a
84 crash between commit and OS flush can lose those bytes.
85 This is the documented "best-effort durability" the abstract
86 contract permits.
87
88 However, FileBackend's relaxed mode **still surfaces write-
89 and commit-side errors immediately** through the call's
90 `expected<>` return arm. It does NOT use the abstract
91 contract's optional deferred-error mechanism. The underlying
92 I/O is synchronous (`::write()` returns before `commit()`
93 runs), so there is no natural moment of deferred discovery
94 for FileBackend — any error is known at the originating call.
95
96 A consequence: callers of FileBackend do not need to call
97 `finalize()` to learn about per-write or per-commit failures.
98 `write().has_value()` and `commit().has_value()` are full
99 immediate signals regardless of durability mode. `finalize()`
100 returns success on a clean FileBackend by construction.
101
102 The `deferred_errors_` member and `finalize()` aggregation
103 path still exist because they're required by the abstract
104 `RecordBackend` interface; for this backend the vector
105 remains empty in practice at this time.
106
107Sub-handle lifetime patterns
108----------------------------
109See `include/utilities/serialization/README.md` for the general
110abstract-surface contract. FileBackend uses:
111
112 - **Writer** (shared-state, thin handle): holds
113 `shared_ptr<FileBackend>` so the parent backend's owned fd and
114 write mutex remain reachable. Writers do not own the fd; they
115 serialize their write+commit through the backend's
116 `io_mutex_`. Multiple Writer handles may coexist on one
117 backend — they take turns through the mutex. The single
118 `::open()`/`::close()` on the fd happens at backend lazy-open
119 / destruction, not per-Writer.
120
121 - **Reader** (snapshot): owns its own `ifstream` (independent
122 read cursor) and a `shared_ptr<const Index>` (the backend's
123 immutable indexed snapshot). Carries its own
124 `IdPredicate` for read-time filtering. Multiple Readers on one
125 backend share the Index via `shared_ptr` aliasing.
126
127Concurrency
128-----------
129Each Reader is a snapshot with an independent ifstream and shares
130the Index only via `shared_ptr` to an immutable value.
131N Readers may be alive and concurrently using the same backend
132without external synchronization.
133Writers are serialized by `io_mutex_` (single-in-flight)
134and may run concurrently with any number of Readers.
135
136FileBackend MUST be constructed via the static `create()` factory.
137The private constructor + factory enforces both the registry
138discipline (no rogue direct instantiation) and the
139`shared_ptr` management the Writer pattern depends on.
140
141Index freshness and the dirty flag
142----------------------------------
143The Index is a point-in-time snapshot. A Writer appending records
144after the Index was built does NOT update the Index — the
145snapshot stays frozen. A `dirty_` flag flipped under the
146`io_mutex_` on every write marks the backend as having had
147post-build appends; the next `reader()` call observes the flag
148and rebuilds the Index before returning the Reader. For the
149canonical "restore at init, save during run" workflow the flag
150never fires after restore-init completes (no one opens new
151Readers after that point). For mid-run restore-after-save it does
152the obvious right thing.
153
154Duplicate-key resolution
155------------------------
156When the index walk encounters two records with the same
157`(id, time_step, checkpoint_epoch)` tuple, the latest-offset
158record wins for lookup and a WARNING is emitted on stderr. This
159makes accidental cross-process collisions visible without
160forcing a policy on the protocol layer.
161*/

287 // the critical section on every `create()` call.
288 static std::mutex registry_mutex_;
289 static std::unordered_map<std::string, std::weak_ptr<FileBackend>> registry_;
