Identity

Three roles, not three independent names.

A formulation has a subject, a locator, and an identity made of the two:

  • subject – get_feature_id, the feature whose data this model reads and produces. Not unique: every model attached to one catchment shares it. Use it to reach forcing and feature data, to name a catchment in a message, and to substitute {{id}} in a config path.
  • locator – get_id, where this sits in that feature's tree of models. The root of that tree is the feature itself, which is why the two hold the same string for a formulation built directly against one. Unique, and what Formulation_Manager keys on.
  • identity – Bmi_Formulation::compound_id(), the locator together with what runs there. Unique, and what serialization records are keyed by, so a restore can tell it is loading into the same model the record came from.

model_type_name is not a fourth identity; it is the component compound_id adds to the locator.

catchment formulation domain layer module 0 of a multi on cat-27
subject cat-27 layer-1 cat-27
locator cat-27 layer-1 cat-27.0
identity cat-27:bmi_c_cfe layer-1:bmi_c_cfe cat-27.0:bmi_c_cfe:bmi_multi_x

Subject and locator diverge only when one formulation composes another. The composer builds each module's locator from its own locator and that module's index within it, so a multi on cat-27 gives its first module cat-27.0; and it hands that module its own subject untouched, so the module still reads cat-27's forcing. Compose once more and the locator grows to cat-27.0.1 while the subject is still cat-27.

A domain layer has no hydrofabric feature, but the layer is still what its model belongs to, so it stands as the subject.

Detailed Description

A model attached to a feature: what is run for that feature, and what it emits.

A formulation is driven by a forcing provider, advances a time step at a time, and emits a set of named output fields. It is identified both by its own id and by the id of the feature it is attached to, which an HY_CatchmentRealization uses to realize that feature.

◆ get_response()

virtual double realization::Formulation::get_response ( time_step_t t_index,
time_step_t t_delta )
pure virtual

Execute the backing model formulation for the given time step, where it is of the specified size, and return the response output.

Advances the model as update does, and additionally reduces its state to one value. Callers that only need the model stepped should use update instead. This function should be implemented and used when a single-value representation of the model's state is required.

Any inputs and additional parameters must be made available as instance members.

The response is a depth, in meters. Implementations are responsible for converting it: the BMI ones ask their model for "m" and convert from whatever it declares in GetVarUnits. HY_CatchmentRealization takes that for granted when it records the response as a depth, and HY_CatchmentArea multiplies it by an area in m^2.

Types should clearly document anything further about their particular response.

Parameters
t_indexThe index of the time step for which to run model calculations.
t_deltaThe duration, in seconds, of the time step for which to run model calculations.
Returns
The response output of the model for this time step, as a depth in meters.

Implemented in Depth_Formulation, realization::Bmi_Module_Formulation, and realization::Bmi_Multi_Formulation.
